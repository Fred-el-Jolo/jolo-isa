# /isa-off and /isa-on: ISA switched off for one session

## Problem

Every prompt of every session goes through the gate: a Jev call under a 1.5 s deadline, and, when Jev isn't sure, a question to the user before the answer (twice in the 2026-10-20 session, for prompts that only asked for an analysis). While ON, the stages, the Stop checks and the perimeter apply to every call. The only way to stop it is `ISA_MODE=off` set when the harness starts: it covers the whole process and can't be switched in a running session.

## Goal

The user types `/isa-off` in a Claude Code or pi session, and from then on, in that session only, every ISA hook is silent: no gate, no Jev call, no stage, no Stop check, no perimeter. `/isa-on` turns it back on, with the ISA or spec that was bound still bound. Every new session starts with ISA on, as today. Only the user's typed command flips it; the model can't.
Said:
- "I would like to have a command setting ISA stuff OFF for a whole session (should be ON by default on every session)"
- "In that case (ISA=OFF), the session should never check for ISA stuff, jev judgements etc ..."
- "can't we use a real claude code command to setup this flag (/isa-off) that records the flag ?"
- "go with B, write the spec": the UserPromptSubmit hook records the flag from the user's prompt; the command file is a stub
- the perimeter while OFF: "Drop it too"
- an ISA or spec bound at `/isa-off`: "Stays bound, frozen"
- turning it back on: "/isa-on"
Assumed:
- the flag is its own key in the session state (`disabled`), next to `mode`, which keeps its meaning (`off`: the gate judges each prompt; `on`: ISA ON); that is what lets `/isa-on` resume the frozen state;
- the shown name of the new state is `DISABLED` (`isa status`, `isa current`, the status line), because `ISA OFF` already names today's default state;
- `/isa-off` and `/isa-on` end the prompt with no model turn; the user sees one line saying what changed;
- only a prompt that is exactly `/isa-off` or `/isa-on` (spaces around it ignored) is the command; the words inside a longer prompt are an ordinary prompt;
- while disabled, prompts are not kept in the session's prompt history, so text typed while OFF can't be quoted as the user's words after `/isa-on`;
- `/isa-off` in a disabled session and `/isa-on` in an enabled one change nothing and say so;
- after `/isa-on`, the next prompt goes through the gate as it would have before `/isa-off`;
- `ISA_MODE` keeps winning: with `ISA_MODE=off` or `on` set, the commands record nothing and say that `ISA_MODE` decides for this process;
- a Claude Code subagent's hook events carry its parent's session id, so a disabled session covers its subagents.

## Out of scope

- An `isa off` / `isa on` CLI command, and Claude Code's `!` shell mode.
- Switching ISA off for a project or for every session: `ISA_MODE` stays for that.
- Carrying the flag to a new session id (a fresh `claude`, `/clear`, a resume that gets a new id): every new session starts ON.
- Labelling the frozen ISA as paused in `isa ls`.

## Constraints

- Only the user sets the flag: in Claude Code from the prompt text of `UserPromptSubmit`, in pi from a registered command. No tool call, no `isa` command and no Skill call sets or clears it.
- A disabled session makes no Jev call and no model turn for the command itself.
- The foundations stay, with one stated exception: a session the user switched off. Foundations.md and SKILL.md say so.
- `runtime/` stays standard-library only, and every file stays under 50 KB.
- Tests touch no real `~/.isa`, `~/.claude` or `~/.pi`: every installer call takes temp paths.

## S1 — The session switch in the engine

The engine (`runtime/isa/engine.py`) gets a session flag, `disabled`, kept in the session state next to `mode`, `bound` and `doc`. Two harness-neutral operations set and clear it: `off` and `on`. Each answers with one line for the user. While the flag is set, every event of that session (session start, prompt, pre-tool, post-tool, tool failure, Stop, compaction, pi's ask answer) returns nothing, before any Jev call, any stage, any classifier or perimeter check, and any write to the session state, except the `on` operation itself. The flag doesn't touch `mode`, `bound` or `doc`, so clearing it brings back the state as it was. `ISA_MODE=off|on` still wins: under it, the operations record nothing and say why. S2 and S3 call these operations; nothing else does.
Accepted when:
- after `off`, a prompt in that session makes no Jev call and returns no context, no warning and no question;
- after `off`, a Write of a project file is allowed in every stage, including TRIAGE with nothing bound;
- after `off`, a Write or a Bash write on an ISA, a spec or a path under `~/.isa` is allowed (no perimeter);
- after `off`, Stop never refuses, and session start and compaction inject nothing;
- after `off`, the session's `mode`, bound ISA and bound spec are the same as before it, and its prompt history doesn't grow;
- after `off` then `on`, the stage is the one before `off`, and the next prompt goes through the gate: the continuation question with an open ISA or spec bound, the work question otherwise;
- `off` answers `ISA OFF for this session — /isa-on turns it back on`; `on` answers `ISA ON again — the next prompt goes through the gate`; `off` on a disabled session answers `ISA is already OFF for this session`; `on` on an enabled one answers `ISA is already ON for this session`;
- with `ISA_MODE=off` or `on` in the environment, neither operation changes the session state, and both answer `ISA_MODE=<value> decides for this process`;
- a second session, with another id, is unaffected by the first one's `off`, and a session never seen before starts enabled.

## S2 — /isa-off and /isa-on in Claude Code

The `UserPromptSubmit` hook recognises a prompt that is exactly `/isa-off` or `/isa-on` (whitespace around it ignored). It runs S1's operation and blocks the prompt: the Claude Code adapter (`cli.py`) gets a new output for a blocked prompt, `{"decision": "block", "reason": "<the line>"}`, so no model turn runs and the user sees the line. The command is recognised in every stage and mode, before the gate, including in a disabled session (that is how `/isa-on` gets through) and under `ISA_MODE`. `install.py` puts two stub command files at `~/.claude/commands/isa-off.md` and `isa-on.md`, with `disable-model-invocation: true` and a description. They make the commands show in autocomplete and `/help`, and keep the model from calling them through the Skill tool. Their body never reaches the model, since the hook blocks the prompt first. The 2026-10-20 probe (scratchpad, Claude Code 2.1.304) showed that the hook receives the raw `/isa-off` before the command expands, and that a blocked prompt runs no model turn.
Accepted when:
- the hook, fed a `UserPromptSubmit` event with prompt `/isa-off`, prints `{"decision": "block", "reason": "ISA OFF for this session — /isa-on turns it back on"}` and the session is disabled; with `/isa-on` it prints the `on` line and the session is enabled;
- a prompt that contains `/isa-off` with other words (`please /isa-off now`) changes no flag and goes through the gate as an ordinary prompt;
- `/isa-off` typed while the gate would ask, while a spec draft is bound, or in BUILD, disables the session in each case;
- `python3 install.py` (temp paths) writes both stub files with `disable-model-invocation: true`; `--dry-run` lists them without writing; `--uninstall` removes them; a file at either path that the installer didn't write is left unchanged and reported;
- no tool call disables a session: a Bash or Write on the session file under `~/.isa/_state` in an enabled session is refused as today, and no `isa` command sets or clears the flag.

## S3 — /isa-off and /isa-on in pi

The pi extension (`adapters/pi/isa.ts`) registers two commands with `pi.registerCommand`: `isa-off` and `isa-on`. Each handler calls `isa hook pi` with S1's operation and shows the returned line with `ctx.ui.notify`. pi runs a registered command without the model, so nothing else is needed. While disabled, the engine returns nothing for pi's events, and the extension already treats an empty result as "go on".
Accepted when:
- the extension test finds both commands registered, and running the `isa-off` handler sends `isa hook pi` the `off` operation for the current session and notifies its line;
- with the session disabled, the extension's `input`, `tool_call` and `agent_before_settle` handlers continue, allow and settle as with an empty result, and add no message for the model;
- a hook error in either handler is caught and shown as a warning, as for the other events.

## S4 — Showing the state

A disabled session shows as `DISABLED` wherever the mode is shown. `status.view` returns `"mode": "disabled"` for it, so `isa status --session <id>` and `isa current` print `ISA DISABLED — <stage> …`. The Claude Code status line renders the same word.
Accepted when:
- `isa status --session <id>` for a disabled session prints a line starting with `ISA DISABLED`, and `--json` has `"mode": "disabled"`;
- after `/isa-on`, the same command prints the mode as it was before `/isa-off` (`ISA OFF` or `ISA ON`);
- the status line renderer test shows `DISABLED` for a `"mode": "disabled"` view.

## S5 — The docs

The documents state the exception. `Foundations.md` and `SKILL.md` say that FOUNDATION_1 and FOUNDATION_2 hold in every session, except one the user switched off with `/isa-off`. `AGENTS.md` (How it is enforced, State, Layout) describes the switch, the stub commands and the `DISABLED` state. The rule block in `skill/global-rules.md` tells the model that only the user turns ISA off, by typing `/isa-off`, so the model offers that instead of trying to switch it off itself.
Accepted when:
- `Foundations.md` and `SKILL.md` name `/isa-off` as the one exception to FOUNDATION_1 and FOUNDATION_2, and agree with each other;
- `AGENTS.md` documents `/isa-off`, `/isa-on`, the stub files installed and the `disabled` session key;
- `skill/global-rules.md` says that only the user turns ISA off, with `/isa-off`;
- `python3 tools/lint_isa.py skill/ISA/Examples/*.md skill/ISA/Examples/specs/*.md` passes, and `rg -n -i 'lifeos|31337|MEMORY/WORK|\btelos\b|\bpulse\b' skill/` finds nothing.

## Decisions

- The hook records the flag from the user's prompt (B), not a command shell line running an `isa off` CLI (A). A needs a CLI that every tool-call path must be kept from; B has one trusted path, the user's typed prompt, and costs no model turn. The 2026-10-20 probe confirmed both work, and that they can't be combined: a blocked prompt doesn't run the command's shell line.
- The perimeter is dropped while disabled, as the user chose: the session is as silent as `ISA_MODE=off`.
- `disabled` is a key of its own, not a third value of `mode`, so `/isa-on` restores the mode and the binding exactly.
